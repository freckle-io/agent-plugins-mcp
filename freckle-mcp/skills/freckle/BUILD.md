# Build, run and change workflows

## Build
- Before writing a new workflow, list the saved ones (`workflows_listWorkflows`, `fields: ["label", "description", "managed"]`). The Workspace often holds Freckle-managed Workflows (`managed: true`) for common jobs such as email to LinkedIn profile or a LinkedIn profile waterfall: connect one to the Dataset as it is when it alone does the job; when the job needs more (reshaped inputs, a route or fallback, or several saved Workflows in sequence), embed each as a step of one new Workflow with its `embed` block and build only the parts no saved Workflow covers.
- Load a CSV of at most 8 KiB (a small local file or pasted rows) into a new Workbook in one call: read the file and pass its text as `workbooks_createWorkbook {payload: {label}, csv: {text, filename, keyColumn}}`, where `csv` is an object (not a JSON string) whose `text` is the CSV itself. It imports the rows and returns the Workbook/Dataset IDs, field catalog, counts and a sample; no upload or wait. For a larger local file, or one whose encoding is uncertain, use `csvUpload: {filename, keyColumn}`: it returns the Workbook/Dataset/Source IDs, an R2 upload command and wait arguments. Run the returned curl with the local path, then call `datasets_waitForCsvImport` with `wait`; an unfinished window resumes with the same Source ID. For an existing Dataset, a CSV of at most 8 KiB goes in one call with `datasets_importDatasetCsv` (payload `{filename, headers, rows, keyColumn}`, rows as objects of strings); a larger file uses `datasets_createCsvUploadUrl` then the same upload/wait path. A failed step keeps the saved resources: follow its recovery details rather than repeating creation. Rows the user adds by hand, such as one example row, use `datasets_createDatasetEntry` to keep the Dataset manually fed; existing rows connect as they are.
- Make one `workflowNodes_listWorkflowNodes` call that searches every provider or capability you plan, separated by `|` (`{ "search": "LeadMagic | Findymail" }`), then get the details and the draft syntax of every planned node missing from that search's `nodeDetails` in one plural `workflowNodes_getWorkflowNodes` call: `{ "definitionKeys": ["theirStackFindJobPostings"], "withSyntax": true }`. Copy exact `definitionKey` values from the catalog, never derive them from labels. The singular `workflowNodes_getWorkflowNode` takes `{ "params": { "definitionKey": "theirStackFindJobPostings" } }`; the plural tool takes a top-level `definitionKeys` array, even for one node, with no `params` or `query` wrapper. When each `|` alternative matches three nodes or fewer, the search usually returns their details and the syntax in `nodeDetails` (left out when they do not fit); use those entries, and skip the plural call when every planned node is already there. Code, Decision, Research Agent and other config-driven nodes show the ports of their config example there, so skip `full: true`. Once the inspected contracts fit the plan, write the whole draft as one JSON object directly in `workflows_buildWorkflow`'s `draft`: no local draft file, and no scripts to generate, validate or patch it (scripts need approval and usually get blocked).
- Judgment on row data (is it B2B software, does it sell to enterprises, which tier the user's written rules give) is a `decision` node (free) with those rules in its question, also when changing a saved Workflow; never keyword or regex matching in `code`. Only exact cutoffs (employee ranges, funding stages) go in `code`, reading the `decision` answers.
- Publish and connect with `workflows_buildWorkflow`; include `sampleRows` only when paid execution is approved. Omit it for build-only work or while waiting for a cost approval. A manual connection does not trigger rows. `connection: { datasetId }` is enough when the inputs are named like the Dataset's fields: it maps them, finds the Workbook and returns the mapping. Fix what it reports and call it again; after a save, change the saved Workflow with `patch`. Connections are manual; automatic triggering is only for webhook feeds, scheduled CRM imports, or a rerun schedule.
- Outputs: one typed result per row, each planned column a visible field in the output Dataset's catalog. A new connection makes one Dataset field per top-level output. Leave out raw provider JSON and pass-through inputs. A stage feeding another workflow outputs the identifiers that stage needs; when the plan lists the intermediate Dataset's fields, each one (carried inputs such as the key and grouped people included) is its own top-level output with that id and type, never a record or evidence object (choose flat fields when the plan allows either), and the next stage declares one input per field.
- A missing input for one part (such as the pitch for message drafts) does not hold up the rest: connect and sample the parts that are ready, and ask for it with the results.
- Stages: for one row per person, push found people to a Dataset and connect the per-person workflow there; for one row per account, keep person slots in one workflow. When a workflow's rows should land one per list item (people grouped per company, scored one per person), output that list as an array of objects and create its connection with `connection: { datasetId, unfoldConfig: { outputId } }`: each item becomes its own row, sibling outputs are not collected, and the unfold is fixed once the connection exists. Never copy a saved Workflow's steps into a new one: embed the saved Workflow instead and build only the new part around it.

## Run
- If a wait ends unfinished, call `workflowRuns_wait` again with the same `runIds`; never re-trigger the run.
- Only when authorized and within the balance; if refused for credits or a member limit, report it and stop.
- A sample is the first rows in list order, 10 unless the user names a number: `sampleRows`, or the first matching rows by id (`datasets_runWorkflowDatasetConnectionEntries`) when the ask selects rows by a value such as a tier. Wait with `workflowRuns_wait`, not sleeps: pass the `runIds` you got, or `connectionId` with `since` set to the `startedAt` the run-starting call returned, so earlier runs do not count.
- To rerun rows on a schedule, make the connection automatic (that runs any pending rows), then `datasets_updateWorkflowDatasetConnectionRerunPolicy`. It starts after each row's next successful run; failed rows never rerun on their own (say so when explaining a missed rerun, and offer `datasets_rerunFailedWorkflowDatasetConnection`). A question about its cost or why it did not run changes nothing: answer it, and offer a run only when the user asks to start or change the schedule. A cron is read in the Workspace zone (`workspace_context` `timeZone`; null is UTC): convert the user's time to it, or set their zone with `workspace_updateWorkspaceTimeZone`.
- When you set, change, pause or explain a rerun policy, call it a Scheduled Workflow in your reply (the app's name: "I set up a Scheduled Workflow that…"). Ask before any run that starts one (rerunning rows, or making a manual connection automatic, which runs its pending rows). A weekday or clock time is a cron (ask the time if none was given); "weekly" or "keep it fresh" is an interval. The stop output is per row (a boolean output, e.g. email found); there is no stop after N rows and nothing more often than daily, so say so and offer the nearest. "Make it automatic" is the automatic trigger; ask whether rows should also rerun on a schedule. Pause = clear the policy (null), not manual; set it again to resume or edit. "When the first finishes run the second" is chaining: connect the second workflow to the first one's output Dataset and make that connection automatic. Tell the user the zone a cron fires in.
- Show what the sample found as a table with one line per sampled row (even a single row) and one column per output, the first column its input key (e.g. the email), and which providers each row went through; flag a column empty on many rows and suggest a waterfall. Then run the rest as approved, and switch to automatic only after the rest has run and another yes.
- A failed sample: fix `invalid_config` or `invalid_input` in a draft you wrote and resample once; `connection` means the user reconnects; for `provider_unavailable` or `internal`, report the step and stop.

## Change a saved workflow
- Read its latest revision. Keep every node, binding, gate, output and row the request does not change exactly as exported.
- New data gets its own new output; new fallbacks and gates follow the [waterfall rules](../freckle-plan/SKILL.md#waterfalls). A value a downstream connection must map (an input carried through) is its own top-level output, since connections map output fields.
- A gate on another workflow's result fails closed: pass only the exact values it emits (`Tier 1`) together with its success `status`, checking no other field (not even one this change adds), and send a missing, empty or malformed object to the skip result. Keep the existing paid nodes, fallbacks and their conditions unchanged, and list every node that starts a path in the gate's pass case, including each fallback's own `if` (the phone fallback's): a fallback condition reading a skipped node's empty output still fires.
- Publish with `workflows_buildWorkflow` (`workflowId`, `expectedRevisionId`, `patch`), producer before consumer. If its inputs change, tell the user which connections will reject. Change Dataset catalogs only when authorized.
- With `workflows_buildWorkflow`, send only the changed parts as `patch` (with `workflowId`), not the whole draft: e.g. `{"nodes":{"gate":{"config":{...}}},"outputs":{"old":null}}`; objects merge, arrays replace, `null` deletes.
- Fill rows a workflow left empty by rerunning only those rows (`datasets_runWorkflowDatasetConnectionEntries`), so results land in the same table.
